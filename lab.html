Get ready · 10 minutes

Create it, open it, understand it.

Everyone creates their own repository and Codespace from the same starting template.

Before you begin

You need a GitHub account with Copilot, access to Codespaces, and permission to use Copilot coding agent and Copilot code review in your repository. Confirm that these are available before starting the lab.

Step 0.1 · Create a repository from the starter template

A repository created from the template gives you an independent copy of the starter project. You can safely create issues, branches, and pull requests without changing the original lab repository.

  • Open the starter repository using the button below.
  • Select Use this template, then select Create a new repository.
  • Choose your personal GitHub account as the repository owner.
  • Name the repository and choose its visibility.
  • Select Create repository and wait for GitHub to open it.
  • In your new repository, select the Settings tab.
  • On the General settings page, scroll down to Features.
  • Select the checkbox next to Issues to enable issues.
Open the starter repository →
Additional instructions for newer GitHub users

A template creates a new repository with its own history, settings, issues, branches, and pull requests. Confirm that the owner shown above the repository name is your GitHub username before continuing. If the Issues tab is not visible after enabling it, refresh the repository page.

Step 0.2 · Create a Codespace from your repository

A Codespace is a cloud-hosted development environment with Visual Studio Code, the repository, runtime, and tools already configured. It gives everyone a consistent workspace without installing the project locally.

  • From your new repository, select the green Code button.
  • Select the Codespaces tab.
  • Select Create codespace on main.
  • Wait for the browser-based VS Code environment to finish loading and dependencies to install.
Additional instructions for newer GitHub users

A Codespace is a complete development environment in the browser. If GitHub asks which repository to use, make sure you select the new repository owned by your account—not the original adu103 template.

Step 0.3 · Install dependencies and run the application

Install the project dependencies, then start the development server so you can see the current application before making changes.

  • Open the terminal in the Codespace using Terminal → New Terminal.
  • Install the project dependencies.
  • Start the development server.
  • When the port notification appears, select Open in Browser and confirm the request tracker loads.
npm install
npm run dev
Additional instructions if a command fails

Check the terminal output for the specific error and retry the command. If the development server starts but no browser opens, open the Codespace Ports tab and select the globe icon beside port 5173.

Repository context · 15 minutes

Tell Copilot how this team builds.

Create repository-wide custom instructions before asking Copilot to plan or implement.

Step 1.1 · Ask Copilot to explain the repository

Start by building shared understanding. Copilot can summarize the architecture and development workflow, but you will verify its explanation against the actual files.

  • Open Copilot Chat in your Codespace.
  • Select Ask mode so Copilot explains without editing files.
  • Submit the prompt below.
  • Compare its response with the files in src, src/lib, and package.json.
Explore this repository and explain:
1. the application architecture and data flow,
2. where business logic and tests live,
3. the commands used to test, lint, and build,
4. the existing coding and accessibility patterns.
Additional instructions for using Copilot Chat

Select the Copilot icon in the Codespace activity bar. The mode selector appears near the chat input. Choose Ask mode before submitting the prompt.

Step 1.2 · Create repository-wide custom instructions

Custom instructions capture durable engineering standards once so Copilot can follow the same expectations while planning, building, and reviewing future changes.

  • In Copilot Chat, select Agent mode.
  • Submit the prompt below.
  • Read the proposed instructions before asking Copilot to create the file.
  • If the proposal looks right, reply Looks good, implement this.
  • Copilot may ask for permission to create files or run commands. Review each request and approve it when it matches this task.
  • Confirm the file is named .github/copilot-instructions.md.
  • Remove anything specific to only one feature; keep durable team standards.
Draft repository-wide Copilot instructions for this project.
Keep them concise and specific. Include:
- strict TypeScript and no `any`,
- React functional components and existing patterns,
- pure business logic in `src/lib` with Vitest coverage,
- semantic HTML and accessible labels,
- reuse of the existing CSS variables and visual style,
- run tests, lint, and build before declaring work complete,
- avoid new dependencies unless they are necessary.

Show me the proposed file before creating it.
Looks good, implement this.
What makes good custom instructions?

Good instructions capture durable team standards, not the details of one issue. Keep them close to the code, review them like code, and update them as the project evolves. Copilot will use this file across planning, implementation, and review.

Step 1.3 · Commit the instructions to your repository

Repository instructions only help GitHub-hosted agents after they are committed and pushed. Treat them as shared project configuration that the team reviews like code.

  • Review the file in the editor one last time.
  • Run the commands below in the terminal.
  • Open your repository on GitHub and confirm the file appears on the main branch.
git add .github/copilot-instructions.md
git commit -m "Add repository Copilot instructions"
git push
Why the push matters

The coding agent runs from the repository on GitHub, not from unsaved or unpushed files in your Codespace. Pushing the instructions makes them available to both coding agent and Copilot code review.

Story A · Plan · 15 minutes

Plan a filter for the request queue.

The first story is guided. Use the provided prompts, but review and improve every result before moving on.

Step 2.1 · Ask Copilot to draft the issue

You are now switching from the IDE in your Codespace to Copilot on GitHub.com. A well-shaped issue becomes the contract for implementation and review, and Copilot can help turn the user need into clear acceptance criteria.

  • Open your repository on GitHub.com.
  • Open Copilot Chat on GitHub.com.
  • Copy the guided prompt below.
  • Submit the prompt in Copilot Chat on GitHub.com.
  • Review the result for a clear user story, testable acceptance criteria, edge cases, and test expectations.
  • Ask at least one follow-up question or request one improvement.
  • When the issue looks ready, reply Looks good—create the issue.
  • Open the newly created issue and confirm it is in your repository.
Help me draft a GitHub issue for the service-request tracker.

User need: As a service desk analyst, I want to filter the request queue by
status and priority so I can focus on the work that needs attention.

Write:
- a concise issue title,
- a user story,
- testable acceptance criteria,
- important edge cases,
- test expectations.

Use the repository's existing UI and architecture. Do not propose an
implementation yet.
Looks good—create the issue.
What a strong issue should cover
  • Status and priority filters can be combined.
  • An unfiltered option is available for each filter.
  • The visible result count updates with the filtered queue.
  • A useful empty state appears when nothing matches.
  • Controls are labeled and keyboard accessible.
  • Filtering logic is unit tested.
Additional instructions for creating the issue

If Copilot asks for confirmation before creating the issue, review the repository, title, and body, then approve the action. You can find the result by selecting the Issues tab in your repository.

Step 2.2 · Use Plan mode before changing code

Stay on GitHub.com and use Plan mode to decide how the change should be made before any code is changed. Saving the approved plan on the issue keeps the implementation approach visible with the work.

  • On GitHub.com, open Copilot Chat while viewing your repository.
  • Select Plan mode.
  • Replace #ISSUE_NUMBER with the issue number you just created.
  • Submit the prompt and read the entire plan.
  • Ask Copilot to revise anything that is missing, unnecessary, or unclear.
  • When every acceptance criterion is represented, reply Looks good—save as a comment on Issue #1.
  • Open Issue #1 and confirm the implementation plan appears as a comment.
Using issue #ISSUE_NUMBER and the repository's custom instructions,
inspect the codebase and create an implementation plan.

Include:
- files to change and why,
- data and state changes,
- accessibility considerations,
- tests to add or update,
- validation commands,
- risks or unclear acceptance criteria.

Do not edit any files yet.
Looks good—save as a comment on Issue #1.
Additional instructions for reviewing the plan

A good plan should identify likely files without inventing a large redesign, isolate filter logic so it can be tested, preserve the existing summary metrics unless the issue says otherwise, and include accessibility and validation steps. You—not Copilot—decide when the plan is ready.

Story A · Build · 20 minutes

Delegate the issue to coding agent.

Let Copilot work asynchronously from the issue and repository instructions you prepared.

Step 3.1 · Assign the issue to Copilot

Coding agent is the asynchronous build path. You delegate a bounded issue, and Copilot works in its own environment to produce a draft pull request for you to inspect.

  • Navigate to the issue you created earlier in your repository.
  • In the right sidebar, select Assignees.
  • Select Copilot and confirm the assignment.
  • If prompted for an environment, use the default environment for your repository.
  • Wait for Copilot to acknowledge the assignment and begin a session.
What happens next

Copilot creates a branch, works in a GitHub Actions-powered environment, runs the project checks, and opens a draft pull request. You can continue working while it runs.

Additional instructions if Copilot is not listed

Confirm you are in the repository created from the template, not the original repository. Coding agent must also be enabled for your account and repository. If it is unavailable, use Agent mode for this story and follow the same issue and review steps.

Step 3.2 · Inspect the coding-agent session and draft pull request

Delegation does not remove oversight. The session log, pull-request diff, checks, and acceptance criteria let you understand the work and steer it when the result needs adjustment.

  • Open the session link shown on the issue and watch the implementation progress.
  • When the draft pull request opens, read its summary and changed files.
  • Confirm the automated tests, lint, and build checks ran successfully.
  • Compare the implementation with every acceptance criterion from the issue.
  • If something is missing, comment on the pull request and mention @copilot.
@copilot Please revisit the acceptance criterion for the empty state.
Keep the existing visual style and add a focused test for the filtering helper.
How to steer without taking the work back

Point Copilot to the missed requirement and describe the expected outcome. Avoid dictating exact code unless the design decision truly belongs to you. The goal is to practice delegating from a well-defined issue.

4
Story A · Review · 15 minutes

Use Copilot code review, then make the decision.

Copilot expands review coverage; you remain responsible for deciding whether the change is ready.

Step 4.1 · Request Copilot code review

Copilot code review provides another set of eyes before a person approves the change. It uses the repository and custom instructions to identify defects, missed cases, and maintainability concerns.

  • On GitHub.com, open your repository and select the Pull requests tab.
  • Open the Story A draft pull request created by Copilot.
  • In the right sidebar, select Reviewers.
  • Select Copilot.
  • Wait for the review to finish, then read every comment before changing code.
Additional instructions for requesting a review

If Copilot already appears as a reviewer, the repository may be configured for automatic reviews. Refresh the pull request and look for a Copilot review under the Conversation or Files changed tab.

Step 4.2 · Triage the review comments

Review comments are recommendations, not decisions. Evaluate each one against the issue, code, and project standards before choosing whether and how to act on it.

  • For each comment, decide whether it is correct, relevant, and worth changing.
  • Apply simple suggestions directly when appropriate.
  • For changes requiring implementation, mention @copilot and ask it to address the accepted feedback.
  • If you reject a suggestion, be able to explain why.
  • Wait for the checks to pass again after changes are pushed.
@copilot Address the review comments that align with the issue's
acceptance criteria. Explain any comment you choose not to implement.
Additional instructions for evaluating a review comment

Trace the comment back to the issue, tests, custom instructions, or an observable defect. A confident-sounding suggestion is not automatically correct. Accept it only when it improves the change without adding unnecessary scope.

Step 4.3 · Review, merge, and run the completed feature

The final approval remains a human responsibility. Review the completed change, merge it into main, then return to your Codespace to pull and run the exact version now stored on GitHub.

  • Open Files changed and read the final diff.
  • Verify every acceptance criterion from the issue.
  • Confirm the tests cover behavior and edge cases, not only implementation details.
  • Confirm the filter controls are keyboard accessible and understandable without color alone.
  • Confirm the implementation follows .github/copilot-instructions.md.
  • Return to the Conversation tab and select Ready for review if the pull request is still a draft.
  • Select Merge pull request, then confirm the merge.
  • Return to your Codespace and open the terminal.
  • Pull the merged changes from GitHub, then run the application.
  • Open the application and confirm the new filtering feature works.
git pull origin main
npm run dev
Where to find the pull request

Return to your repository on GitHub and select the Pull requests tab. The coding agent's draft pull request should appear there and should also be linked from the Story A issue.

Story B · Plan, Build, Review · 35 minutes

Repeat the workflow with less guidance.

Add a way to resolve a request. This time, you write the Copilot prompts and build interactively in Agent mode.

Step 5.1 · Plan: write your own issue-drafting prompt

Return to your repository on GitHub.com and repeat the planning skill with less scaffolding. You have the user need and quality expectations, but you will decide how to give Copilot enough context to draft useful work.

User need: As a service desk analyst, I want to mark an active request as resolved so the queue and summary metrics reflect completed work.

  • On GitHub.com, open your repository and Copilot Chat.
  • Ask Copilot for a concise title and user story.
  • Ask for testable acceptance criteria.
  • Include accessibility and already-resolved edge cases.
  • Ask for test expectations without prescribing the implementation.
  • Review and improve the draft, then create the issue in your repository.
Additional guidance—not a prompt to copy

A strong issue should ensure open and in-progress requests can be resolved, already-resolved requests do not offer the action, summary metrics update immediately, the action has an accessible name and focus treatment, and the status-update logic is tested. Create it from the Issues tab in your repository.

Step 5.2 · Plan: write your own Plan mode request

Return to your Codespace and create the implementation conversation yourself. A strong Plan mode request defines the outcome and constraints without prescribing code that Copilot has not yet investigated.

  • In your Codespace, open Copilot Chat and select Plan mode.
  • Reference the Story B issue and the repository custom instructions.
  • Ask Copilot to inspect the codebase before proposing changes.
  • Require the plan to cover files, state changes, accessibility, tests, validation, and risks.
  • Do not tell Copilot which files to edit or what the implementation must be.
  • Review and revise the plan until every acceptance criterion is covered.
Questions to ask yourself before accepting the plan
  • Is the proposed change small and consistent with the existing app?
  • Is status-update logic separated so it can be unit tested?
  • Will the summary values update from the same source of truth?
  • Does the plan address keyboard use and already-resolved requests?

Step 5.3 · Build: create a branch and use Agent mode

Continue working in your Codespace. Agent mode is the interactive build path: Copilot changes the code while you watch, answer questions, and redirect the implementation as it unfolds.

  • In the Codespace terminal, create a branch named feature/resolve-request.
  • Switch your working branch to feature/resolve-request.
  • In the Codespace, switch Copilot Chat to Agent mode.
  • Write your own implementation request using the issue and approved plan.
  • Tell Copilot to follow the custom instructions, add focused tests, and run test, lint, and build checks.
  • Watch the changes as they happen. Pause and redirect Copilot if it moves beyond the issue scope.
git branch feature/resolve-request
git switch feature/resolve-request
What your Agent mode request needs to contain

Reference the issue number and approved plan, require compliance with .github/copilot-instructions.md, require focused tests and all validation commands, and ask for a final summary. Write the request yourself rather than copying a supplied prompt.

Step 5.4 · Build: verify, commit, and open a pull request

Working code is not complete until you have inspected it, exercised the user experience, run the project checks, and packaged the change for review in a pull request.

  • Review every changed file before committing.
  • Run the application and resolve at least one open request.
  • Confirm the action is absent for an already-resolved request.
  • Confirm the queue summary updates immediately.
  • Run all automated checks.
  • Commit and push the branch.
  • Navigate to your repository on GitHub.com.
  • At the top of the repository, find the message that feature/resolve-request had recent pushes.
  • Select Compare & pull request.
  • On the pull-request page, under Add a description, select Copilot, then select Summary.
  • Review the generated description, then select Create pull request.
npm test
npm run lint
npm run build
git add .
git commit -m "Add request resolution workflow"
git push -u origin feature/resolve-request
Additional instructions for opening the pull request

Before creating the pull request, confirm the base branch is your repository's main branch and the compare branch is feature/resolve-request. Make sure the generated description links to the Story B issue and accurately explains the change and validation performed.

Step 5.5 · Review, approve, and merge the pull request

Use the same review process regardless of whether a person or agent wrote the code. Evaluate Copilot's feedback, complete the human review, and merge the finished change into main.

  • Request Copilot as a reviewer on the Story B pull request.
  • Triage each review comment and make only the changes you agree with.
  • Re-run checks after any review-driven changes.
  • Perform your own review against the issue and custom instructions.
  • Compare this interactive workflow with the delegated Story A workflow.
  • If another participant is reviewing your work, ask them to submit an Approve review. GitHub does not allow you to approve your own pull request.
  • When the pull request is ready and all checks pass, select Merge pull request and confirm the merge.
Additional instructions for the human review

Check correctness, edge cases, accessibility, test quality, maintainability, and unnecessary complexity. Copilot's review is evidence to consider, not the approval decision.

Story B complete

You have now taken two features through planning, implementation, Copilot code review, human review, and merge using two different build approaches.

Wrap-up · 10 minutes

Compare the two ways of working.

Both paths use the same issue, repository context, checks, and pull request process.

Step 6.0 · Keep using the same loop

The workflow is designed to repeat. Choose another small user need, shape it into a clear issue, plan the work, build it with the Copilot approach that fits, review the pull request, and merge it.

  • Try adding another feature to the service-request tracker.
  • A dark theme would be a useful next story: define how the user switches themes, how the preference is preserved, and what accessible contrast means for the application.
  • Write the issue and acceptance criteria yourself rather than copying a supplied prompt.
  • Choose coding agent for well-bounded delegated work or IDE Agent mode when you want to steer interactively.
  • Repeat the same Plan → Build → Review → Merge loop.

Coding agent

  • Best for a well-defined, bounded issue.
  • Works asynchronously while you do something else.
  • Returns a draft PR for review and iteration.
  • Benefits heavily from clear acceptance criteria and custom instructions.

IDE agent mode

  • Best when you want to steer decisions as the work unfolds.
  • Keeps the developer close to the code and running application.
  • Makes it easy to pause, inspect, adjust, and continue.
  • Uses the same repository standards and validation commands.

What you should leave knowing

  • The quality of the implementation starts with the quality of the issue.
  • Custom instructions carry team standards across the entire workflow.
  • Plan mode is where people shape the approach before code changes.
  • Coding agent and IDE agent mode are two execution choices, not two separate processes.
  • Copilot code review improves coverage and speed; a person still owns approval.
  • GitHub keeps the issue, plan, code, discussion, checks, and decision connected.

Final reflection

Compare the two complete workflows and identify where each approach fits your own software-development work.

  • Which story was easier to delegate, and why?
  • Where did Copilot need more context than you expected?
  • Which Copilot code-review comments were valuable? Which were not?
  • What would you add to the custom instructions before starting the next issue?
  • When would you choose coding agent versus IDE Agent mode on your own work?
